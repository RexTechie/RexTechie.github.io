## 研究背景与问题

从自然语言需求直接生成完整软件仓库（NL2Repo）不同于函数级代码补全：系统需要规划目录与模块、保持跨文件接口稳定、管理依赖，并修复只在集成或执行阶段暴露的不一致。现有多智能体软件开发系统、仓库级代码生成方法和工具型 SWE agent 分别覆盖了角色协作、仓库上下文或执行反馈，但没有同时把架构契约、跨文件协调和迭代修复纳入从空工作区开始的完整流程（§1–§2.4）。

## 核心贡献

1. 提出 CodeTeam：多个 Architect agent 竞争生成软件设计草图（SDS），CTO agent 选择并归一化为机器可检查契约，Developer agent 按依赖实现，Git 协作与 QA agent 驱动定向修复。
2. 在 SketchEval 上进行受控比较，并在 NL2Repo-Bench 上引入执行型外部验证，使结构相似度和上游测试通过率形成互补证据。
3. 通过移除 RAG、动态开发者分配和 Git 协作的消融，分析规划、任务分工和修复协调各自的作用。

## 方法或系统架构

### 需求预处理与软件设计草图

系统把 README 风格的需求文档作为输入，先做规则化处理：统一标题、展平嵌套列表，只保留包含命令、配置键或 API 示例等可执行信息的代码块，并删除徽章、图片、变更日志、发布说明和贡献者信息。输出带有稳定的章节标记，供后续组件按标题引用需求，而不是依赖原始行号（§3.2.1）。

每个 Architect agent 生成一个结构化的软件设计草图（Software Design Sketch，SDS）。SDS 不是仅供阅读的计划，而是控制后续生成的机器可检查契约，至少包含 `tech_stack`、`repo_tree`、`developer_plan` 和 `files` 四类字段。它记录语言、框架、测试框架和依赖；固定的仓库文件树；每个文件的职责、公开接口、所有者和依赖；以及开发者数量和文件所有权映射。SDS 必须可解析为 JSON；文件必须出现在文件树中，所有者必须在开发者计划中声明，依赖边必须指向已声明的文件或导出符号，文件级依赖图在合并同文件符号引用后必须无环。不能通过这些检查的候选仍会被记录，但不会交给 CTO 选择（§3.2.2）。

### Architect 竞争与可选的检索增强

默认配置实例化 4 个 Architect agent。它们独立提出候选 SDS，并同时决定项目所需的 Developer 数量和文件归属。为了避免候选设计趋同，系统随机化生成顺序，为不同 Architect 指定不同偏好（例如最小化架构与分层架构、类组织与函数组织），并只向后续 Architect 暴露已经出现的顶层模块名和高层设计意图摘要，而不暴露完整候选方案（§3.2.3）。

启用 RAG 时，系统从公开仓库构成的设计语料中检索默认 top-5 设计参考。参考项不是大段原始代码，而是 README 摘要、文件树、依赖模式、文件角色摘要和导出接口提示。Architect 只把它们当作模块划分、依赖选择、文件边界和团队组织的设计线索，并要求根据当前需求生成原创 SDS。提交前，Architect 会执行与解析和结构有效性检查相近的轻量自检。

### CTO 选择与契约归一化

CTO 阶段先自动过滤 JSON 解析失败、缺失所有权、文件引用无法解析、符号声明不一致或文件级循环依赖的候选。对剩余候选，CTO agent 按结构有效性、接口一致性、在依赖与资源约束下的可实现性、开发者数量和文件归属是否适合仓库规模四项打分，每项 0–2 分，总分范围为 0–8。总分相同时，优先选择未声明假设更少、跨模块依赖扇出更低的方案（§3.2.4）。

选定的 SDS 会被归一化：规范化路径、去重符号、解决命名冲突、物化开发者到文件的映射，并构建文件级依赖图。如果归一化失败，则尝试下一个最高分的有效候选。归一化后的 SDS 成为 Developer 和 QA agent 的唯一事实来源。

### 依赖感知的开发者分工与执行

CodeTeam 以文件任务为实现粒度，且任务池受 SDS 中的开发者计划约束。每个 Developer 只拥有一组文件；系统为目标文件构造紧凑上下文，包括相关 SDS 片段、目标文件当前内容，以及依赖文件的接口简报。接口简报只包含文件路径、导出符号、可用时的类型签名、不变量和最新 `update_reason` 摘要；每个任务最多额外请求两个接口简报，不读取其他开发者拥有文件的完整内容（§3.2.5）。

调度器维护一个由依赖满足情况决定的 ready queue，并把就绪文件派给记录的所有者。没有前置依赖的文件优先；同一 Developer 的多个就绪文件按下游依赖链长度、直接依赖者数量和 SDS 文件顺序排序。Developer 完成文件后在隔离分支提交，并通过结构化提交消息报告目标文件、修改的导出符号、兼容性说明和受影响的依赖文件。系统随后更新接口索引、刷新依赖简报，并把新满足依赖的文件加入队列。若接口发生变化，受影响的依赖文件可以回到队列，由其原所有者修复（Algorithm 1；§3.2.5）。

### Git 协作、QA 反馈与终止

QA agent 在依赖层或小批量文件完成后，根据 SDS 和需求生成轻量临时测试，在临时 QA 目录中执行并在最终评测前删除。这些测试不影响 SketchBLEU、仓库大小统计或最终文件树。QA 将结果标准化为问题记录，包含症状类别、traceback 或断言消息、疑似源文件和最小修复范围（§3.2.6）。

当多个文件都出现错误时，QA 依次检查接口一致性、依赖方向、源文件自身的结构有效性和最小修复范围：默认只重新排队依赖链中最早违反接口或语法约束的源文件；只有问题影响公开 API、导入路径或共享配置时，才扩大到下游文件。循环在 QA 完成一轮验证且没有失败、达到 QA 迭代上限、或耗尽全局时间/令牌预算时终止（§3.2.6）。

## 实验设置

### 研究问题与受控评测

RQ1 研究工作流型多智能体系统是否提升 NL2Repo 结果，并用 NL2Repo-Bench 的执行验证检查结构改进是否转化为可执行正确性；RQ2 隔离 Architect 阶段的检索增强对架构设计的影响；RQ3 分析动态开发者分配、依赖感知执行和 Git 协作对仓库生成的影响（§3.1）。

SketchEval 包含 19 个真实 Python 仓库、对应需求文档和参考实现，按难度分为 easy 5、medium 8、hard 6。输入是处理后的需求文档，输出是在空工作区生成的完整仓库。主指标 SketchBLEU 由四种信号构成：线性化代码的 n-gram 重合、对定义/导入/返回/控制结构关键字加权的 n-gram 重合、目录树与文件级语法骨架的结构相似度，以及函数级符号/API/导入关系的数据流语义相似度（§3.3）。

比较对象覆盖单 agent Vanilla、多智能体软件开发 ChatDev、通用自主 agent AutoGPT 和此前的 NL2Repo 方法 CodeS。CodeTeam 和 CodeS 都评估 prompt-engineering（PE）及 supervised fine-tuning（SFT）版本；主干模型为 Qwen2.5-72B，方法使用相同解码超参数和计算预算。每种方法用 3 个随机种子运行，报告均值与标准差，并使用 Wilcoxon signed-rank 检验和 bootstrap 置信区间比较任务级差异（§3.3）。

Architect RAG 语料先审计仓库名、GitHub 来源、README、包命名空间、依赖清单、顶层文件树和项目描述，排除 fork、镜像、重命名版本、教程模板、基准派生项目及目标仓库近重复项。剩余仓库被转换为包含 README 摘要、顶层文件树、依赖清单、文件角色和接口摘要的块，按 768 tokens 切分、128 tokens 重叠，用 BGE-M3 嵌入并以 FAISS 的 HNSW 索引检索。查询时从不同仓库取 top-5，并过滤近重复块、完全相同文件树和与当前任务高度相似的块（§3.3.3）。

### 执行型外部验证

NL2Repo-Bench 包含 9 类 Python 库的 104 个任务，按 easy 26、medium 46、hard 32 划分，平均输入约 18.8k tokens。每项任务从单一自然语言说明和空工作区开始；生成仓库必须满足包布局、依赖声明、导入一致性和功能正确性，并由原始上游 pytest 套件执行验证。CodeTeam 遵循 document-only 设置，不接触目标仓库、脚手架或测试用例；生成过程内部使用其多智能体工作流，完成后交回原始评测器。所有方法在 104 个任务上使用与 SketchEval 相同的 3 个随机种子，报告平均测试通过率和 Pass@1，并按难度分解。由于成本较高，该基准用于 RQ1 的外部验证，不重复完整消融（§3.4）。

### 消融与诊断设置

消融均在 CodeTeam-PE、相同 Qwen2.5-72B 主干、解码配置和计算约束下进行：去掉 Architect RAG；去掉 SDS 中的动态开发者数量和所有权，改成固定 4 个 Developer 的轮询分配；或去掉分支协作与结构化 `update_reason`。除最终 SketchBLEU 外，RAG 消融记录 SDS 解析成功率、结构有效率和候选计划多样性；开发者分工消融记录 QA 轮数、跨文件接口不匹配失败数和每次 LLM 调用的平均上下文规模（§3.5）。

## 主要结果

在 SketchEval 上，CodeTeam 的 PE 与 SFT 版本都超过对应 CodeS 版本，提升主要集中在结构和数据流子分数；在 NL2Repo-Bench 上，结构级优势也转化为更高的上游测试通过率。完整任务一次成功仍然困难，说明从空工作区生成可执行仓库与提升平均测试通过率是不同层次的目标（§4.1–§4.2）。

## 消融、成本与失败分析

去掉 RAG 会削弱架构规划，去掉动态开发者分配的影响最大，去掉 Git 协作的下降较小但仍保持一致。动态分工把平均 QA 轮数从 5.2 降到 3.6，把接口不匹配失败从 12.4 降到 7.8，并把平均上下文从 4.4k 降到 3.1k；去掉 Git 协作则使接口不匹配从 7.8 小幅升至 9.1。QA 的首轮修复贡献最大，后续轮次收益递减（§4.3–§4.4）。

轻量 QA 仍可能漏掉上游测试才会暴露的空输入、边界条件和返回类型错误；SDS 强制的文件边界也可能把逻辑耦合的操作拆开，导致跨模块数据流问题。论文将这些失败视为结构协调已经改善、但执行反馈仍不够丰富的剩余问题（§5.1.1；§6.1）。

## 优点与局限

### 优点与创新

1. SDS 把目录、接口、依赖和所有权变成可解析契约，使架构决策能够约束后续实现并可追踪。
2. 动态开发者分配是针对具体项目的工作流决策，不把团队规模和文件归属固定成全局超参数。
3. 受控的 SketchEval 与执行型 NL2Repo-Bench 互补，且使用多随机种子、统计检验和公开代码增强了复现线索。

### 作者自述局限

1. 实验只覆盖 Python 仓库，没有覆盖更大规模、混合语言或复杂构建/测试流水线；因此结论限定在给定基准设置内（§6.3）。
2. QA 使用根据 SDS 和需求生成的轻量测试，而不是评测用的上游测试；它可能漏掉逻辑和边界错误，论文把接入更丰富的执行、静态分析、调用图和类型推断反馈列为后续方向（§5.1.1；§7）。
3. RAG 语料、嵌入模型、top-k、Architect 数量和 CTO 评分规则主要由初步实验确定；单因素消融不能穷尽组件间的协同或干扰，且基准污染风险无法完全排除（§6.1–§6.4）。

### 阅读分析

1. 论文同时报告 SketchBLEU 和上游测试通过率，但 NL2Repo-Bench 的完整任务 Pass@1 仍低，说明当前工作流更可靠地改善了仓库结构和平均测试覆盖，而不是彻底解决端到端生成。
2. 动态分工的收益同时来自更合适的所有权和更紧凑的上下文，仍可用更细的成本—质量实验区分两者；论文现有消融把它们作为一个工作流组件处理。

## 与 AutoBackend / AutoFullStack 的关系

- **关系与差异**：本轮没有提供 AutoBackend / AutoFullStack 的现有架构说明；若它们面向后端或全栈项目级生成，CodeTeam可对应其中的需求分解、接口契约、文件级分工和验证闭环，但论文只验证 Python 仓库生成，不直接覆盖前端、数据库和部署联调。
- **可借鉴设计**：可以把服务/模块接口、所有权、依赖方向和测试入口写成机器可检查的中间契约，再用依赖感知调度和最小范围修复降低跨模块返工；迁移时需要用真实构建、集成测试和运行时反馈替换轻量 QA。
- **新研究问题**：在全栈仓库中，SDS 是否需要同时表达 API、数据库 schema、前端数据流和部署资源；跨语言依赖变化时，怎样定义可局部修复且不破坏契约的反馈粒度。
