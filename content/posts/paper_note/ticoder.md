## 研究背景与问题

仓库级代码生成需要在有限上下文中处理跨文件依赖。已有方法常用 RAG 或先生成实现计划再检索潜在被调用函数，但存在两个缺口：计划多从自然语言需求出发，缺少测试用例提供的边界行为约束；函数检索多依赖需求与函数描述的语义相似度，忽略函数实现逻辑以及仓库中真实的调用方式，导致“找到了函数却不会正确复用”（§1–§3）。

## 核心贡献

1. 提出测试驱动的迭代规划，用需求和测试用例生成实现步骤，再由 judge-and-reflection 循环评价覆盖性、一致性、独立性和粒度。
2. 提出实现感知的仓库复用：以功能相似度和实现相似度联合检索 callee function，再按调用图结构与困惑度筛选代表性 usage patterns。
3. 在 CoderEval 和 DevEval、三种主干 LLM 及多个 RAG/规划基线下评估，并通过组件、规划轮数、相似度权重和 usage pattern 数量实验分析机制。

## 方法或系统架构

TICoder 包含三个阶段：测试驱动迭代规划、实现感知复用和增强代码生成（§4.1）。给定开发者需求 `r` 和测试用例 `t`，系统先生成实现步骤集合 `s`。对每个步骤，从仓库函数语料 `C={(f_j,d_j)}` 中检索潜在 callee function，随后为每个 callee 找到 caller functions 并选出代表性调用模式，最后把需求、测试、检索函数和调用模式一起交给 LLM 生成代码。调用模式的相关性用条件困惑度衡量，困惑度越低表示上下文越能帮助模型预测该调用模式（§4.2）。

### 测试驱动迭代规划

需求通常描述核心功能，却不完整描述无效输入、空值和其他边界行为；测试用例可以作为行为规格补充这些信息。TICoder 先由 LLM-as-a-planner 根据需求和测试用例生成初始实现步骤。每一步应清晰、无歧义且可验证；显式覆盖边界条件和预期处理；声明外部函数、模块或库的依赖；保持可维护性；并保持合适的功能边界、避免不必要副作用。步骤数量自适应决定，但受预设上限 `n_s` 约束（§4.3.1）。

随后由 LLM-as-a-judge 对步骤进行结构化评价，维度包括：是否覆盖全部功能且与测试行为一致；步骤是否足够独立、可单独实现或修改；以及分解粒度是否既不粗到缺少可执行细节，也不细到引入不必要复杂度。每个维度按 0–100 分并给出文字理由；若未达到阈值，评价反馈与需求、测试和当前步骤一起返回 planner 继续修订，直到达到标准或达到最大迭代次数 `n_i`（§4.3.2）。

### 双视角 callee function 检索

仅按步骤与函数描述的语义相似度检索，可能找到“说得像”但实现逻辑不匹配的函数。为此，TICoder 让 LLM 为每个实现步骤生成一个自包含代码片段 `c_i`，作为 step-aware code representation。对步骤 `s_i`、其代码表示 `c_i`、候选函数 `f_j` 及其描述 `d_j` 分别构造向量，定义功能相似度 `Sim_F` 为步骤向量与描述向量的余弦相似度，定义实现相似度 `Sim_I` 为代码表示向量与函数实现向量的余弦相似度。联合得分为：

\[
Sim(i,j)=\alpha Sim_F(i,j)+\beta Sim_I(i,j),\quad \alpha+\beta=1。
\]

候选函数按联合得分降序排列，每个实现步骤选取排名最高的潜在 callee（§4.4.1）。

### 双阶段 usage pattern 选择

获得 callee 后，系统使用开源 LSP 构建 Repository Call Graph，找到调用该 callee 的 caller functions。第一阶段按 caller 所调用函数集合进行结构聚类：调用集合相同的 caller 归入同一簇。每簇选取困惑度最低的 caller 作为中心，以压缩结构重复的示例。第二阶段把所有簇中心按困惑度升序排序，为每个 callee 选择前 `n_p` 个代表性 usage patterns。这样既保留函数的实际调用方式，又控制冗余上下文（§4.4.2；Algorithm 1）。

### 增强代码生成

系统把检索到的 callee functions、选出的 usage patterns、测试用例和原始需求拼接为最终提示，生成目标代码。论文特意保留原始需求，而不是只把实现步骤交给生成器；实现步骤用于规划和检索，需求与测试仍是最终行为约束（§4.5）。

## 实验设置

### 研究问题与数据集

RQ1 比较 TICoder 与基线在仓库级代码生成上的总体性能；RQ2 通过消融评估规划、测试、迭代、双视角检索和 usage pattern 选择；RQ3 研究规划迭代次数；RQ4 研究功能相似度与实现相似度的权重；RQ5 研究每个 callee 选取的 usage pattern 数量（§5.1）。

实验使用 CoderEval 和 DevEval。CoderEval 包含来自 43 个项目的 230 个 Python 任务及来自 10 个项目的 230 个 Java 任务；DevEval 包含来自 GitHub 真实开源项目的 1,825 个 Python 任务。每项任务都提供人工编写的需求和用于验证功能正确性的测试用例（§5.2）。

### 基线、模型与指标

基线包括 SimpleRAG（按功能相似度检索代码片段）、RepoCoder（迭代检索—生成）、A³Codgen（局部、全局和第三方库信息）、AllianceCoder（从实现步骤检索潜在 API）、RLCoder（用强化学习优化检索器）和 RepoScope（调用链感知的多视角上下文）。TICoder 与基线都使用 GPT-4o-mini、DeepSeek-V3 和 Qwen2.5-Coder-7B 作为代码生成主干（§5.3）。

功能正确性通过执行测试用例并计算 Pass@k 评估。若每个需求生成 (n_g) 个样本，其中 (c) 个通过测试，则使用标准 Pass@k 估计在 (k) 次采样中至少有一个正确样本的期望概率（§5.4）。

### 实现与运行设置

规划阶段把最大实现步骤数 `n_s` 设为 5；planner、judge 的选择和最大迭代次数通过 RQ3 分析。检索阶段使用 GPT-4o-mini 为实现步骤生成代码表示；judge 阈值设为 90。系统使用 OpenAI `text-embedding-3-small` 编码实现步骤、步骤代码、仓库函数及其描述，再计算功能和实现相似度；usage pattern 数量由 RQ5 分析。GPT-4o-mini 使用 `gpt-4o-mini-2024-07-18`，DeepSeek-V3 使用 `DeepSeek-V3-0324`，Qwen2.5-Coder 使用 Hugging Face 上的 7B 基础模型；前两者通过官方 API 调用（§5.5）。

## 主要结果

TICoder 在 CoderEval 的 Python/Java 及 DevEval、三种主干模型上均超过基线，论文报告跨设置的总体提升约为 11.25%，且与最强基线的差异达到统计显著。消融显示，测试用例、双视角检索和代表性调用模式都对仓库级生成有独立贡献，但过多迭代或过多调用模式会引入噪声（§6.1–§6.5）。

## 消融、成本与失败分析

在 DevEval 的 GPT-4o-mini 设置下，去掉规划、测试用例、迭代、单一相似度视角、usage patterns 或双阶段选择都会降低 Pass@1。去掉生成阶段的测试用例影响尤其明显；只把实现步骤而不是原始需求交给生成器时下降更大，说明规划步骤不能替代原始需求与测试的行为语义（§6.2）。

规划迭代总体有益，但随次数增加并不单调；不同 planner 和数据集的最佳次数不同，过度修订可能增加噪声。usage pattern 从 1 增至 2 能改善表现，继续增至 3 则下降，同时令 token 消耗增加，体现上下文丰富度与冗余之间的折中（§6.3；§6.5）。

论文的案例显示，纯语义检索可能选中功能描述相近但参数或实现逻辑不适合的 callee；usage pattern 能补充参数配置、调用条件和仓库惯用方式。作者也指出，高质量测试用例在真实仓库中并不总是存在，且 prompt 设计和参数设置会影响 judge-and-reflection（§7.1–§7.2）。

## 优点与局限

### 优点与创新

1. 将测试用例前置到实现计划阶段，使测试从最终判分器变成行为规格和边界条件提示。
2. 把“函数是否相关”和“函数如何实现”分开建模，并进一步检索真实调用上下文，减少只提供孤立代码片段的问题。
3. 在 Python 与 Java 的仓库级基准、多个闭源/开源主干和统计检验下保持一致趋势，机制消融也与总体结果相互印证。

### 作者自述局限

1. 真实仓库场景中可能没有高质量测试用例，这会限制测试驱动规划的适用性（§7.2）。
2. judge-and-reflection 的效果依赖 prompt 模板；论文通过抽样任务和有经验程序员迭代模板，但不能保证覆盖所有规划与评价维度（§7.2）。
3. DevEval 中有一部分任务是独立函数，不一定需要规划或 callee 检索；论文采用自适应规划让单步表示“不需要规划”的情况，但任务分布仍会影响结论（§7.2）。

### 阅读分析

1. TICoder 的测试使用是“测试驱动规划 + 最终提示约束”，不是在生成后运行测试并自动修复；因此它与真正的执行反馈闭环仍有边界。
2. 实现相似度需要先让 LLM 为规划步骤生成代码表示，额外模型调用和嵌入成本应与 Pass@k 提升一起报告；当前设置给出了 token 消耗分析，但没有完整的端到端成本曲线。

## 与 AutoBackend / AutoFullStack 的关系

- **关系与差异**：本轮没有提供 AutoBackend / AutoFullStack 的实现细节；若它们生成的是带有既有仓库和测试的后端/全栈项目，TICoder 更接近“需求到修改”的仓库级上下文增强，而不是从空工作区生成完整系统。
- **可借鉴设计**：可以把接口契约、数据库访问模式、前端调用模式和测试行为作为检索信号；对每个实现步骤同时检索语义相关性、实现逻辑和真实调用样例，并限制样例数量以控制上下文。
- **新研究问题**：测试用例不完整或跨服务时，怎样自动区分“缺失行为规格”和“实现错误”；调用图、API schema、数据库 schema 与 UI 状态流能否共同构成全栈 usage pattern。
